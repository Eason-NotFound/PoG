# PoG 四角色 UI 设计 · v1（门户演示草案）

状态：门户界面设计参考。当前实现仅为本地演示 API、存储及固定 AI 数据，尚未接入独立后端或链上合约。

现行 V2 接口以仓库内 Solidity、packages/contract-abis/v2 和 docs/M2_V2_INTERFACE_IMPLEMENTED.md 为准。资金先释放给 Foundation，后续供应商结算单独确认；本文件保留的直付、旧函数名和页面 API 是历史 UI 拟案，不是生效的合约协议。具体差异见 docs/PORTAL_V2_BOUNDARY.md。

## 1. 本版产品边界

- 一个 Next.js 应用，四个角色工作区：捐款人、基金会、受捐机构、管理员。不是四套互不相通的应用。
- 原方案中的 Verifier 审核功能放在基金会工作区，使用独立审批权限；不能因登录基金会角色就自动获得签名权。管理员不默认兼任付款审批人。
- Vendor 是已认证供应商，拥有收款资料与测试钱包；本版不新增第五个门户。由受捐机构代传供应商文件，并记录原始出具方和上传人。
- Booth 默认：捐款人模拟 HKD 支付；基金会 Treasury 向 Escrow 注入 mHKD；采购完成后合约向 Vendor 支付 mHKD。MockHKD 无真实价值，并非 RedCoin。
- 模拟支付确认、基金会注资确认和供应商付款确认是三种不同事件。捐款记录本身不意味着 Escrow 已有对应可用资金。
- 核心流程：创建项目 → 捐款确认及项目备资 → 采购需求/报价 → AI 采购前审核 → 人工采购批准 → 链上预算预留 → 发出 PO → 交付验收 → 最终发票/证据 → AI 最终审核 → 人工付款批准 → Relayer 付款 → 链上确认 → 捐款去向分配。
- 优先完成验收后供应商直付。小额垫付报销保留独立页面设计；预付款/订金、真实银行接入、退款执行、争议治理与 Merkle 验证完整链路按后续接口和优先级接入。
- UI 可以展示未接入功能，但按钮需明确标识“未接入”，不可假装操作成功。

## 2. 统一界面规范

桌面布局：左侧 208px 导航，顶部角色/机构与全局入口，主内容居中，详情采用双栏或三栏。手机折叠菜单，表格改记录卡片，详情顺序堆叠，按钮不依赖悬停。

视觉：深绿色主操作、浅灰背景、白色内容面，金额用等宽数字，图表保持克制。备选为蓝色主色；浅/深色随系统。中文为默认，保留英文业务缩写 PO、GRN、AI、Hash。

共同顶部：PoG 标识、当前项目（有多个时）、全局 Hash 查询、通知、当前账户。基金会和管理员按权限显示钱包状态；捐款人和受捐机构不强制显示连接钱包按钮。页脚显示“演示环境 / 数据更新时间”，技术连接细节放管理员页。

页面共同结构：标题和主要操作 → 待办/关键金额 → 列表或表单 → 记录详情。每个页面有加载、空数据、无权限、请求失败与重试状态。

金额单位：捐款侧为 HK$（模拟支付）；链上资金为 mHKD。两类账本并列展示，不能直接加总。小数精度从资产配置读取；HKD 分与代币最小单位分别存储，显式换算并记录演示 1:1 映射。

## 4. 捐款人 UI 详细设计

### D01 我的总览 · /donor

顶部显示累计已确认捐款、已分配支出、待分配余额；余额注明“捐款归属账本”，不承诺均可立即提取。主体展示最近捐款、所支持项目的最新进展。主要按钮为“探索项目”；每条记录可“查看去向”。

如果 Merkle 证明尚未接入，显示“分配明细已生成，链上证明未生成”；若付款尚未完成，显示“项目已预留预算”，不显示“你的捐款已经使用”。

### D02 探索项目 / 项目详情 · /projects、/projects/:id

项目列表：名称、基金会、公益类别、目标、模拟 HKD 已筹金额、期限、状态；支持关键词与类别筛选。

项目详情：项目简介、受捐机构、预算用途、项目规则及版本、公开支出、脱敏交付证据。捐款统计与 mHKD 项目资金池使用两个独立区块。

主要操作：“支持这个项目”“查看公开账本”“查看项目规则”。公开页面不展示未经授权的个人资料、银行账户、完整票据。

### D03 捐款 · /projects/:id/donate

两步表单：

1. 金额：HK$100 / 300 / 600 / 自定义；公开署名/匿名；可选留言；勾选已阅读项目规则。
2. 确认：项目、金额、模拟支付方式、资金用途、规则版本；按钮“确认模拟捐款”。

状态：待确认 → 模拟支付处理中 → 支付已确认 / 失败。成功页给出 Donation ID、金额、收据 Hash 与“查看捐款”。后台登记或资金映射延迟单独显示“同步中”。不能把演示按钮伪装成真实 FPS/信用卡付款。

### D04 我的捐款 · /donor/donations

列表字段：Donation ID、项目、金额、支付状态、已分配金额、时间。详情包含 paymentConfirmationHash、捐款单内容 Hash、关联注资批次（如有）、项目规则 Hash。

操作：“查看详情”“下载捐款证明”“查看去向”“复制 Hash”。捐款证明称为 PoG 捐款记录，不暗示可交易 NFT 或税务收据。

### D05 资金去向 · /donor/donations/:id/allocations

按已确认付款列出采购编号、公开用途、供应商公开名称、总支出、此捐款分配额、付款交易 Hash、分配批次。

演示例：A/B/C 捐款 600/300/100，实际付款 200 后分别分配 120/60/20。A 页面显示已使用 120、未分配 480。

“验证去向证明”展开 donationId、procurementId、allocatedAmount、batchId、leaf、proof、root、链上锚定状态。前端必须实际用约定编码和链上 root 核验，不能只信任 API 的 verified 字段。输出“验证通过 / 不匹配 / 尚未锚定 / 暂不可用”。此证明证明分配记录与 root 一致，不证明现实交付一定真实。

“提出疑问”记录问题、关联采购与凭证；它不会自动冻结合约。正式争议处理未接入时，标记为待人工处理。

## 5. 基金会 UI 详细设计

### F01 工作台 · /foundation

四个资金指标：累计注资 Deposited、可用 Available、预留 Reserved、已付 Paid；退款在资金明细显示。独立展示模拟捐款已收与待映射金额。

待办按“采购前审批 / 最终付款审批 / 待补件 / 执行异常”分组。主要按钮“处理审批”；次要按钮“创建项目”“项目注资”。

### F02 项目与预算 · /foundation/projects

创建/编辑字段：名称、简介、目标、期限、Recipient、预算类别与额度、单笔限额、审批门槛、供应商白名单、退款/剩余资金规则。风险阈值显示当前规则，不能任意在单笔审核时改动。

流程：保存草稿 → 规则预览 → 授权发布 → 链上登记中 → 已发布。规则修改生成新版本并保留旧规则，已批准采购不能静默切换规则。

资金页：“项目注资”输入项目与 mHKD 金额，显示 Treasury 余额、Escrow 地址与 allowance；必要时先授权，再 depositToProject。两笔交易分别显示状态，链上确认后 Available 才增加。

### F03 采购前审批 · /foundation/procurements/:id/review

三栏布局：左侧采购与报价证据，中间 AI 报告，右侧人工决策。

采购字段：Recipient、用途、类别、物品/数量/单价、合计、选定 Vendor、预计交付、项目规则版本、类别余额。

AI 区：采购前报告、六维风险（文档、重复、预算、供应商、三单匹配、交付证据）、原因码、证据定位、报告版本/Hash/有效期。不适用的维度显示“本阶段不适用”，不能伪造零分。

操作：“要求补充”“拒绝申请”“批准采购并签名”。冻结/争议入口仅对具备权限且接口已接入者显示。批准弹窗列出采购编号、Vendor、金额、poHash、证据摘要、有效期和签名账户。

点击批准后：准备 ApprovalIntent → 核对 → 钱包 EIP-712 签名 → API 验签保存 → Relayer 排队 → 链上预算预留 → BudgetReserved 事件确认。页面显示“已签名，预算预留处理中”，而不是立即“预留成功”。

PO 在预留前形成待发出的锁定版本以供签名；预算确认后再正式发给供应商。更改供应商、金额或 PO 内容使旧审批失效，需重新审批。

### F04 交付与付款 · /foundation/procurements/:id/payment

上部为 PO / 最终 Invoice / GRN 三单对比，突出数量、单价、金额及 Vendor 差异；附件包含签收照片。右侧展示最终 AI 风险和第二阶段人工审批数。

付款条件逐项显示：已预留、已验收、最终发票存在、AI 报告有效、未冻结、Vendor 仍认证、签名门槛满足、金额不超预留、未付款。

操作：“要求补充”“拒绝付款”“批准付款并签名”。批准后由 Relayer 执行 executePayment；收到 PaymentExecuted 确认后显示“已支付供应商”。基金会无须再手工构造付款交易。

若最终发票低于预留，确认框显示“付款金额 / 剩余预留 / 拟释放金额”；释放需要实际事件确认。若超过预留，阻止批准，引导“申请变更”。采购阶段签名不可复用为付款签名。

### F05 供应商 · /foundation/vendors

认证状态、公开名称、允许的项目、认证钱包、必要脱敏收款资料。可提交供应商认证申请、选入项目白名单。修改收款地址创建变更申请，不允许在已签名付款单内临时覆盖。

### F06 账本与证明 · /foundation/ledger

分页记录注资、预留、释放、付款与退款；按项目、资产、日期、采购编号筛选。点击记录查看业务 Hash、交易 Hash、事件和来源证据。

分配批次显示“待计算 / 明细已生成 / 待锚定 / 已锚定 / 失败”；重试仅对允许任务开放，不是重新付款。账本可导出授权范围内的数据。

## 6. 受捐机构 UI 详细设计

### R01 我的工作台 · /recipient

显示参与项目、可申请类别预算、我的待处理采购、待补件、待验收。主要按钮“新建采购申请”。时间线展示“已提交 → 初审 → 采购批准 → 预算预留 → 交付验收 → 终审 → 供应商收款”。

这里不显示“我的可提现余额”；项目资金不会任由受捐机构提现。

### R02 项目预算 · /recipient/projects/:id

项目目标、允许预算类别、可申请余额、单笔限额、报价要求、可用供应商。主要操作“按此预算申请采购”。预算与其他采购并发变化时，提交后需以后端和合约校验为准。

### R03 新建采购申请 · /recipient/procurements/new

四步表单：

1. 项目与用途：项目、类别、采购说明、预计交付日期。
2. 物品与供应商：名称、规格、数量、单价；后台计算总额；选择已认证 Vendor。
3. 报价与证据：报价单、适用时的三份报价、选中报价及理由、采购请求文件。
4. 预览并提交：金额、Vendor、所需证据、规则版本；生成采购编号与内容 Hash。

操作：“保存草稿”“下一步”“返回修改”“提交采购申请”。提交后自动排入采购前 AI 审核；状态中显示任务进度与失败重试。

### R04 采购详情与补件 · /recipient/procurements/:id

显示锁定内容、PO、审批结果、AI 可见原因、待补清单、时间线和 Hash。按钮“补充资料”“查看 PO”“上传交付证据”。草稿可编辑，已提交版本不可覆盖；补件产生新版本并重新审核。

### R05 交付与发票 · /recipient/procurements/:id/delivery

字段：实际交付时间、每项交付/验收数量、验收人、验收说明、GRN、最终发票、送货单、签收照片。

供应商发票可由受捐机构代传，记录 uploader 与 issuer。页面并排展示 OCR 原始抽取值与用户修正值，修正有记录，修改后重新审核。

操作：“上传文件”“保存草稿”“提交验收与最终证据”。提交后进入第二次 AI 审核，然后等待基金会人工付款审批。最后显示“供应商已收款”，不是“受捐者到账”。

缺货、数量不符时显示差异并阻止正常完成流程；部分交付/部分付款在完整合约支持前不能通过界面按钮绕过。

### R06 小额报销 · /recipient/reimbursements（扩展页）

针对允许的授权垫付：项目、类别、日期、事由、费用项、原始收据、实际付款证明、垫付人、核验后的收款资料。

校验小额上限、禁止拆单、重复凭证、关联方规则，经过 AI 和人工审核。此类付款对象与供应商直付不同，必须使用单独业务类型和适配流程。

本轮给出完整表单和状态设计；在合同规则和支付接口确认前标记“报销流程待接入”，不复用供应商直付函数假装完成报销。

## 7. 管理员 UI 详细设计

### A01 系统总览 · /admin

展示未认证机构/供应商、待处理异常、AI 任务状态、Relayer 队列、事件索引延迟、数据库/链对账结果。业务统计按币种和账本区分。

### A02 用户与机构 · /admin/organisations

账户、机构类型、认证资料、角色、钱包绑定与状态。操作为“查看证明”“批准认证”“要求补充”“拒绝”“停用平台账户”。敏感操作填写原因并记录审计。

演示角色入口只在 Demo 模式出现；正式权限由后台决定。管理员不能自行把任意页面切换成他人的账户。

### A03 供应商认证 · /admin/vendors

查看 KYB/收款证明、钱包、关联项目及变更历史，执行认证/补件/拒绝。停用供应商时显示受影响的未付款采购；付款前再次验证其状态。

### A04 审计与 Hash · /admin/audit

按业务编号、Hash、角色、动作、请求 ID、时间筛选。查看业务快照、操作历史、AI 报告、两阶段签名摘要、链上交易映射和对账差异。

不能删除或覆盖已确认交易、审批快照、已提交凭证；更正通过新版本或纠正事件完成。

### A05 系统连接 · /admin/connections

只读展示前端/API 版本、数据库、私有文件存储、AI 服务、Anvil 网络、三个合约地址/版本、Relayer、Event Indexer、最近确认区块与最后同步时间。

按钮“检查连接”“查看失败任务”“重试同步”。同步重试不重新发起付款。业务动作重试前先查询原任务、交易和 nonce，避免重复执行。

### A06 演示管理 · /admin/demo

展示 Demo 账户和演示项目。未来可接入“初始化演示”和“重置测试场景”，仅限演示管理员，执行前列出影响并确认；设计预览不执行重置或铸币。主界面明确所有资金均为模拟。

## 8. 公共页面、Hash 与凭证

登录：演示使用预设角色账户入口；应用登录与钱包签名分离。基金会审批时检查钱包角色和网络。注册/邮箱验证/密码找回属于后续账号体系，不阻挡 Booth 三端演示。

公共记录详情：类型、编号、版本、金额、业务状态、当前处理人/任务、附件、时间线、Hash、链上事件。通知点击可直达对应记录；敏感内容按角色过滤。

Hash 查询包含类型选择：单据内容 / 文件 / 交易 / AI 报告 / 项目规则 / 证据 Root / 分配 Root。交易查询还需网络；支持自动搜索但不靠长度断言类型。

查询过程：输入完整 Hash → API 查询 Hash 索引 → 权限检查 → 返回匹配记录与版本 → 授权读取数据库/私有文件 → 按需要核验链上登记。

返回字段：记录类型、业务编号、版本、项目、时间、公开摘要、核验结果、存证状态、相关交易列表；多结果时呈现列表。

关键区分：

- 业务单据的内容 Hash 标识提交时的不可变快照；后续审批/付款状态用关联事件保存，不放回快照导致 Hash 改变。
- 文件 Hash 按原始字节计算，可对应多个业务引用；扫描或裁剪会改变文件 Hash，查重还需要业务指纹。
- 交易 Hash 标识某网络上的交易，不等于单据 Hash；同一采购有登记、预留、付款等多笔交易。
- Root 是证据集或分配批次的承诺，不能直接当作单个文件下载地址。
- 有 Hash 不等于已上链；已上链不等于发票真实；能输入 Hash 不代表有权读取敏感附件。
- 对未授权私密记录统一提示“未找到可访问记录”，避免泄露其存在。

重要记录至少包括：捐款单、采购单、PO、发票、GRN、报销单、AI 报告、项目规则和分配批次。每种记录保存 ID、版本、算法、规范化方式、Hash 与对象关联。

## 9. 状态、异常与权限

业务状态主线：DRAFT → SUBMITTED → AI_PRECHECKED → PURCHASE_APPROVED → RESERVED → DELIVERED → AI_FINAL_CHECKED → PAYMENT_APPROVED → PAID；UI 额外显示 PO 待发出、待验收、待补件等子步骤，最终枚举以 ABI 为准。

独立状态：AI 任务、人工审批、Relayer 任务、链上交易、文件处理、分配证明。人工已签名与链上已确认必须独立。

异常：NEEDS_INFORMATION / FROZEN / DISPUTED / CANCELLED；冻结不能靠普通批准按钮解除。

风险策略按项目规则展示：共享方案曾建议低风险仍需人工、中风险补件、更高风险多人复核、80–100 冻结。Booth 1-of-1 仅用于符合低风险规则的案例；最终规则与阈值由区块链组接口决定，不能用演示单签覆盖高风险门槛。

覆盖的 UI 失败：加载失败、空列表、无权限、会话过期、文件错误、上传失败、AI 超时、签名取消/过期、网络错误、余额不足、Vendor 状态改变、重复提交、旧版本冲突、交易回滚、长时间 pending、索引延迟。全部给出可执行下一步。

审批前回读当前状态和版本。单笔重复点击使用幂等键；两个审核者并发时展示最新门槛与有效签名数，不能重复计票。

## 11. 数据库存储边界

| 实体 | 保存内容 | UI 提取用途 |
|---|---|---|
| users、sessions、role_assignments、wallets | 账户、会话、机构角色、验证钱包；若以后用密码，仅安全密码散列 | 登录、权限、签名账户 |
| organisations、vendors、verification_cases | Foundation/Recipient/Vendor 资料、认证与变更 | 认证页、供应商选择 |
| projects、rule_versions、budget_categories | 规则快照、预算、Recipient、供应商白名单、规则 Hash | 项目、预算及审批 |
| donations、payment_events | 模拟支付金额/币种、paymentEventId、状态、确认 Hash | 捐款与凭证 |
| funding_batches、funding_links | Treasury 注资、对应捐款批次、映射金额/单位、确认交易 | 避免捐款与资金池注资混同/重复分配 |
| procurements、items、quotations、purchase_orders | 采购与费用项、报价、选定 Vendor、PO 版本 | 申请、初审 |
| deliveries、invoices、evidence_files | GRN、验收项、票据抽取、私有文件键、SHA-256、上传人/出具方 | 验收、三单匹配 |
| ai_assessments、audit_findings | 两阶段报告、风险、原因码、模型版本、报告 Hash、有效期 | AI 报告与条件检查 |
| approval_intents、signatures | 阶段、锁定版本、Vendor/金额/PO/证据、nonce、期限、签名 | 审批与重放防护 |
| reservations、payouts、budget_ledger | 预留、释放、供应商付款及其真实状态 | 资金指标与账本 |
| document_versions、hash_index | 对象 ID、类型、版本、算法、规范化版本、内容 Hash、权限 | Hash 调取确定的原记录 |
| allocation_batches、allocation_entries、proofs | donation ↔ procurement、分配最小单位、批次、leaf/proof/root、锚定状态 | 个人捐款去向证明 |
| outbox、jobs、chain_transactions、chain_events | 执行请求、重试、交易、网络/区块/事件序号、确认状态 | Relayer 与前端同步 |
| reimbursements、questions、notifications、audit_logs | 扩展报销、疑问、通知、操作历史 | 报销与公共工作流 |

原始附件保存在私有对象存储，数据库保存索引、权限和必要结构化内容；前端不能直接连接数据库。原始 KYC、完整票据与银行资料不上公共链。

Hash 由服务端按固定规范计算；文件 SHA-256、规则/业务 JSON 规范化方式和合约 bytes32 编码统一约定。敏感低熵信息公开承诺需考虑随机盐，不能把可枚举的个人字段直接裸哈希公开。

审批状态与交易 Hash 不纳入原单据快照；后续变化独立关联。业务指纹与文件 Hash 不混用。一个文件 Hash 可关联多个记录；一个交易可有多个事件，按 network＋txHash＋logIndex 去重。

## 12. 连接与联调设计

技术方向：Next.js + TypeScript 门户；FastAPI + PostgreSQL API/数据层；私有文件存储；Anvil；MockHKD、PoGRegistry、ProcurementEscrow。独立 AI 服务、Relayer 与事件索引器仍需接线，现行合约接口以 V2 ABI 为准。

建议本地端口：Web 3000、API 8000、Anvil RPC 8545、PostgreSQL 5432；这些是本设计建议，均可配置，以团队部署配置为准。

三台 Booth 电脑访问同一中央机器的 Web/API，共享同一数据库和链；不能把各台电脑的 localhost 当成同一服务器。基金会钱包 RPC 指向中央机器；前端/API 的来源、CORS 与会话配置对应同一部署。

角色页面用事件推送或短轮询刷新工作流；链上 Indexer 延迟显示“同步中”和最后更新时间。金额成功仅依据核验后的事件，不依据按钮被点击、签名已提交或浏览器本地变量。

资金守恒以已确认链上账本为准：deposited = available + reserved + paid + refunded。模拟 HKD 捐款和 mHKD Treasury 资金分开对账。额外的 Treasury 预充值未映射为捐款时，不能自动归属于某个捐款人。

Allocation 仅在供应商付款确认后生成最终分配，按相同资产/项目的有效映射余额分配；批次幂等、整数尾差处理、总和等于对应支出。尚未映射或资助来源不足时显示待对账，不伪造捐款去向。

对接区块链组所需：最终 ABI、地址、chainId、RPC、角色账户、EIP-712 domain/types、两阶段 nonce/期限规则、事件字段、错误码、token decimals、PO/evidenceRoot 编码、人工签名门槛、部分付款/释放支持范围。

## 13. 第一版实施范围与验收

P0：四门户、演示角色登录、项目/预算、模拟捐款凭证、项目注资状态、采购/报价、两阶段 AI 报告、两阶段人工签名、预算预留、验收/发票、供应商付款结果、Hash 权限查询、完整时间线、连接状态。

P1：捐款分配/Merkle 实际验证、多签演示、争议处理、退款执行、小额报销、真实账号注册。P1 页面布局先设计好，未接入时明确显示状态，不挤占 P0 闭环。

设计确认后先交付可在 VS Code 运行的完整前端与 Mock API 适配、演示数据、环境配置示例和启动步骤；之后连接真实 FastAPI、数据库与 ABI。Mock 模式持续可见标识，不能宣称已经完成真实后端/链上联调。

三端演示验收：捐款人确认模拟捐款 → 基金会资金映射/注资 → 受捐机构提交采购 → AI 初审 → 基金会签名预留 → 受捐机构提交交付证据 → AI 终审 → 基金会签名付款 → 三端看到同一已确认结果。异常演示为重复票据或高风险证据进入冻结，不能付款。

本设计定义页面结构、视觉与功能范围。真实合约方法及数据协议须依据区块链接口校准。

## 14. 已确认的权限调整（2026-10-02）

角色权限采用以下规则：

- 普通捐款人：仅捐款人工作区。
- 基金会：捐款人＋基金会工作区；捐款人视角只能查看本账号的个人捐款。
- 受捐机构：仅受捐机构工作区。
- 管理员：四个工作区均可查看，另管理工作人员的页面授权；查看权不自动成为资金审批权。
- 页面维护人员：独立身份，管理员逐页勾选，可跨工作区但只能进入获授权页面。默认只读。

管理员可新增维护人员账号、分配/撤销页面、停用账号。页面导航、直接 URL 和 API 都使用服务端权限；授权变更在下次请求生效。参见 docs/PERMISSIONS.md。

四角色 UI 已进入编码阶段，初版为本地演示数据＋真实服务端访问控制。真实区块链接口、数据库及 AI 待后续联调，不视作已完成。
