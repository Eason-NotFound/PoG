## 场景 A：60/40 捐入，72 兑付，剩余28退款

使用默认 `P-001` 项目。同一浏览器多角色需分别退出/登录；不同浏览器或独立配置文件更方便。

1. Donor A（donor）：兑换60，再点同一按钮一次。HKD 1000→940，测试币只增加60。捐入 `P-001` 60。
2. Donor B（donor2）：兑换40，捐入 `P-001` 40。项目累计100。
3. admin：演示批准拨款 `PO-72`，金额72。
4. Foundation：刷新，确认测试币72、模拟HKD仍0。选择 `PO-72` 兑付72；完成后模拟HKD72、测试币0。
5. 再次兑付此笔72，即使换新幂等键也必须被阻止。不得出现“供应商已收款”状态或供应商账本。
6. Foundation：申请关闭，填写原因。admin先尝试关闭核账，应因未结采购被阻止。
7. **纯演示** admin：登记模拟外部核账引用 `EXTERNAL-72`，代表 Foundation 已在本模块外处理后交回凭证；该操作不转账、不扣HKD。然后关闭核账。
8. Donor A 可退16.8，B可退11.2。分别领取后项目 Closed，退款总额28。
9. A可再把16.8测试币换回模拟HKD，HKD 940→956.80。

anvil模式第3步改为原采购/人工审批流程的真实拨款；第4步前先关联事件。第7步必须在原合约流程记录外部结算并完成原人工审批。Payment 不生成结算签名、不替 Foundation 付款。

## 场景 B：暂停后取消，未支出资金全额退款

使用 `P-REFUND`（或新一轮独立项目），不要复用已Closed项目。

1. A/B分别兑换并捐入60/40。若与场景A金额相同，先点“开始新一笔操作”创建新的兑换请求。
2. Foundation暂停该项目。新的捐款与兑付被阻止；此时领取退款也失败，因为尚未核账。
3. 测试恢复后项目可重新接受操作，再次暂停。
4. Foundation申请关闭，admin关闭核账。未支出/未预留/无未结采购，退款池100。
5. A领取60，B领取40。重复点击原请求不重复到账；换新请求也不能重复领取。

## 异常阻断

| 操作 | 预期 |
| --- | --- |
| Donor越权兑付/暂停 | 403 |
| 模拟HKD不足或测试币不足 | 409，余额不变 |
| `60.001`、负数、数字类型金额 | 400 |
| 同一幂等键更改金额 | 409 |
| 重复关联同一拨款/采购 | 409 |
| 暂停/Closing时捐款 | 409 |
| 有预留或未结采购时关闭 | 409或链上预检失败 |
| 非原Donor领取 | 阻止 |
| Registry全局暂停 | 新捐款/兑付阻止；其他调用由原合约控制 |
| RPC超时 | 待核对并冻结可用额；不得自动重发 |
| 错误的恢复txHash/nonce/回执 | 阻止记账 |
| Anvil重置/部署清单不匹配 | 拒绝复用旧轮次账本 |
| Foundation退回已释放资金 | Closing才允许；原V2未结采购仍须后续处理 |
